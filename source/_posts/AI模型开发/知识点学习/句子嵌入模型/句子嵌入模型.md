句子嵌入模型会把 query、标题或段落编码为固定维度向量，让语义接近的文本在向量空间中更靠近。几行代码就能得到 embedding，但一个可用的检索系统远不止“算向量，再取余弦相似度”。

真实项目中最棘手的问题通常是：离线挑两句话看起来很相似，接入知识库后却漏召回；模型升级时指标提升，上线后反而退化；向量检索找到了语义相关内容，却漏掉了错误码和版本号。

这些现象分别涉及任务定义、数据、切块、编码约定、索引、混合检索和版本切换。本文用一个问题驱动的完整链路把它们串起来。

## 一、先问清楚：你需要的是“相似”，还是“能回答”

下面两句话语义很接近：

```text
A：Redis 缓存穿透是什么？
B：Redis 缓存雪崩是什么？
```

它们共享 Redis、缓存和故障主题，但 B 不能回答 A。如果训练数据只标注“主题相似”，模型可能把它们拉得很近；检索任务却需要判断“文档能否满足 query”。

常见 embedding 任务至少有三类：

| 任务 | 样本关系 | 主要指标 | 典型用途 |
| --- | --- | --- | --- |
| 语义相似度 | 两句话表达是否接近 | Spearman、Pearson | 去重、改写识别、STS |
| 信息检索 | 文档能否满足查询 | Recall@K、MRR、NDCG | 搜索、RAG、推荐召回 |
| 表示学习 | 向量是否利于下游任务 | 聚类或分类指标 | 聚类、分类、异常检测 |

项目启动时应先写出一个可验收的问题：

> 对真实用户 query，在 P95 低于 80 ms 的约束下，正确证据进入前 20 个候选的比例是多少？

它比“训练一个中文 embedding 模型”更有用，因为它同时定义了数据、指标、候选规模和性能预算。

## 二、双塔为什么快，又为什么需要 reranker

检索型 embedding 通常采用 bi-encoder，也叫双塔：

```text
query --------> encoder --------> query vector
                                      |
                                      | similarity
                                      v
document -----> encoder --------> document vector
```

文档向量可以离线计算，线上只编码 query，再在索引中做近邻搜索。这使它适合百万甚至更大规模的候选库。

代价是 query 和文档在编码时没有逐 token 交互。Cross-Encoder 会把 query 和候选文档一起输入模型，匹配更细致，却必须对每个候选重新推理，无法直接扫描整个语料库。

因此常见链路是：

```text
BM25 / 向量检索召回 100 条
              ↓
          合并与去重
              ↓
       Cross-Encoder 精排 20 条
              ↓
       返回搜索结果或交给 LLM
```

双塔负责“不漏掉”，reranker 负责“排得准”。如果正确文档没有进入召回候选，后面的 reranker 再强也无法恢复。

## 三、最小推理示例：query 和 document 必须遵守同一套约定

下面使用 Sentence Transformers 的官方接口演示一个小型语义检索。示例会下载模型，需要在项目自己的虚拟环境中安装并锁定 `sentence-transformers` 版本；不要安装到系统 Python。

```python
from sentence_transformers import SentenceTransformer

model = SentenceTransformer("sentence-transformers/all-MiniLM-L6-v2")

documents = [
    "Use json.load to read JSON from an opened file object.",
    "Use json.loads to parse JSON from a string.",
    "Use python -m venv to create a virtual environment.",
]
query = "How can I parse a JSON file in Python?"

# 检索任务优先使用 query/document 专用入口。模型若定义了 prompt 或路由，
# 两个入口会应用对应约定；普通无 prompt 模型的结果可能与 encode() 相同。
document_vectors = model.encode_document(
    documents,
    normalize_embeddings=True,
)
query_vector = model.encode_query(
    query,
    normalize_embeddings=True,
)

# L2 归一化后，点积等于余弦相似度。
scores = document_vectors @ query_vector
ranking = sorted(
    enumerate(scores.tolist()),
    key=lambda item: item[1],
    reverse=True,
)

for index, score in ranking:
    print(f"{score:.4f}\t{documents[index]}")
```

当前 Sentence Transformers 文档建议：检索任务有明确 query/document 区分时使用 `encode_query()` 与 `encode_document()`；其他任务可使用 `encode()`。旧版本可能没有这两个入口，不能为了照抄示例而混装版本，应按项目锁定版本使用等价的 prompt 约定。

### 为什么要显式归一化

余弦相似度为：

\[
\cos(q,d)=\frac{q\cdot d}{\lVert q\rVert_2\lVert d\rVert_2}
\]

如果 query 和文档都做 L2 归一化，范数均为 1，公式就变成点积：

\[
\cos(q,d)=q\cdot d
\]

这不代表所有模型都必须归一化。有些模型按点积或其他约定训练。真正的原则是：训练、离线建库、在线查询和评估必须一致，并与模型说明保持一致。

最危险的情况不是“都不归一化”，而是文档建库时归一化、在线 query 却没归一化，或者索引配置用余弦、服务代码却按未经确认的点积阈值过滤。

## 四、看起来只是字符串，实际包含六个版本契约

同一段文本经过以下任一变化，向量都可能不同：

1. tokenizer 或词表变化；
2. query/document prompt 变化；
3. 最大长度和截断方向变化；
4. pooling 从 mean 变为 CLS；
5. 是否 L2 归一化变化；
6. 模型、adapter 或精度变化。

例如训练时使用：

```text
query: Redis 如何避免缓存穿透？
passage: 可以使用布隆过滤器或缓存空值。
```

线上若直接编码原始 query，模型收到的任务信号就不同。对 E5、instruction embedding 或非对称模型，这种差异可能非常关键。

不要在服务中自己重写 pooling，除非模型本来就是你用原始 Transformer 模块组装并训练的。Sentence Transformers 模型通常已经保存 tokenizer、Transformer、pooling、normalize 和 prompt 等配置，直接加载完整模型更安全。

## 五、数据不是越多越好，而是关系要与任务一致

检索训练最常见的数据形式是：

```json
{
  "query": "C++ 条件变量为什么会虚假唤醒？",
  "positive": "wait 返回不保证条件为真，应在循环中重新检查谓词。",
  "hard_negative": "notify_one 会唤醒一个正在等待的线程。"
}
```

正样本必须能满足 query，而不是只共享主题。hard negative 则应“很像但不能回答”，它能迫使模型学习细粒度边界。

### 常见数据来源及偏差

| 来源 | 优点 | 必须警惕的偏差 |
| --- | --- | --- |
| 点击日志 | 贴近真实流量 | 位置偏置、热门偏置、误点击 |
| FAQ 关系 | 结构稳定 | 问法单一，覆盖不了长尾表达 |
| 人工标注 | 质量可控 | 规则不一致、成本高 |
| LLM 改写 | 扩充快 | 模板化、语义漂移、事实错误 |
| 旧系统召回 | 易挖 hard negative | 会继承旧系统盲区 |

数据集切分应按文档、用户会话或时间边界分组。同一文档的相邻 chunk 若分别进入训练和测试，测试指标会因为内容重叠而虚高。

数据清洗、去重、标签审计、分组切分和 hard negative 的细节见[数据处理与数据集评估](/notes/ai模型开发/知识点学习/句子嵌入模型/数据处理与数据集评估/)。

## 六、loss 应服务于样本关系

### Multiple Negatives Ranking Loss

每个 query 的 paired document 是正样本，同 batch 的其他 document 被当作负样本。它能高效利用 batch，但对重复文本和假负样本敏感。更大 batch 提供更多负样本，不等于自动提供更好的负样本。

### Triplet Loss

输入 anchor、positive、negative，要求正样本比负样本更近并满足 margin。它直观，但效果依赖负样本难度和 margin。

### 相似度回归

对有连续相似度标签的 STS 任务，可以让模型拟合余弦分数。它训练的是语义相似，不应未经检验就当作问答检索目标。

### 蒸馏

可让 Cross-Encoder 或更大 embedding 模型为候选对打软分数，再训练小模型逼近。教师模型的偏差同样会被学生继承，因此要用真实检索测试集验收。

显存有限时，可以使用 [LoRA 微调](/notes/ai模型开发/知识点学习/句子嵌入模型/lora微调训练/)，但 LoRA 只改变参数更新范围，不改变上述任务逻辑。

## 七、为什么只看相似句示例会误判模型

拿三句话观察余弦分数只能验证模型会运行，不能证明它适合语料库。检索评估至少需要：

```python
queries = {
    "q1": "SSE 断线后怎样续传？",
    "q2": "如何读取 JSON 文件？",
}

corpus = {
    "d1": "服务端发送 id，浏览器重连时携带 Last-Event-ID。",
    "d2": "json.load 接收已打开的文件对象。",
    "d3": "json.loads 用于解析字符串。",
}

relevant_docs = {
    "q1": {"d1"},
    "q2": {"d2"},
}
```

Sentence Transformers 提供 `InformationRetrievalEvaluator`，可从这三组映射计算 Recall、MRR、NDCG、MAP 等指标：

```python
from sentence_transformers.evaluation import InformationRetrievalEvaluator

evaluator = InformationRetrievalEvaluator(
    queries=queries,
    corpus=corpus,
    relevant_docs=relevant_docs,
    name="knowledge-base-dev",
    mrr_at_k=[10],
    ndcg_at_k=[10],
    precision_recall_at_k=[5, 10, 20],
)
metrics = evaluator(model)
print(metrics)
```

不同指标回答不同问题：

- Recall@K：正确证据有没有进入候选集；
- MRR：第一条正确证据出现得是否足够靠前；
- NDCG：有分级或多个相关结果时，整体排序是否合理；
- Precision@K：前 K 条中有多少确实相关。

RAG 首阶段通常优先保证合理候选规模下的 Recall，再让 reranker 和上下文选择提高精度。但 K 过大也会增加重排成本和噪声，不能无限扩大。

### 一个无需第三方依赖的指标检查器

指标实现很容易因分母定义而混淆。下面代码用于理解单相关或多相关检索中的 Recall@K 和 MRR@K，可直接运行：

```python
from collections.abc import Mapping, Sequence, Set

def recall_at_k(
    predictions: Mapping[str, Sequence[str]],
    relevant: Mapping[str, Set[str]],
    k: int,
) -> float:
    scores = []
    for query_id, expected in relevant.items():
        if not expected:
            continue
        retrieved = set(predictions.get(query_id, ())[:k])
        scores.append(len(retrieved & expected) / len(expected))
    return sum(scores) / len(scores) if scores else 0.0

def mrr_at_k(
    predictions: Mapping[str, Sequence[str]],
    relevant: Mapping[str, Set[str]],
    k: int,
) -> float:
    reciprocal_ranks = []
    for query_id, expected in relevant.items():
        reciprocal_rank = 0.0
        for rank, document_id in enumerate(
            predictions.get(query_id, ())[:k], start=1
        ):
            if document_id in expected:
                reciprocal_rank = 1.0 / rank
                break
        reciprocal_ranks.append(reciprocal_rank)
    return (
        sum(reciprocal_ranks) / len(reciprocal_ranks)
        if reciprocal_ranks
        else 0.0
    )

predictions = {
    "q1": ["d3", "d1", "d4"],
    "q2": ["d2", "d3", "d1"],
}
relevant = {"q1": {"d1"}, "q2": {"d2"}}

assert recall_at_k(predictions, relevant, 1) == 0.5
assert recall_at_k(predictions, relevant, 2) == 1.0
assert mrr_at_k(predictions, relevant, 2) == 0.75
print("metrics OK")
```

评估集还应按 query 类型切片：精确术语、口语改写、否定问题、时间敏感问题、长尾领域词。总分提升可能掩盖最重要场景的退化。

## 八、为什么有了 embedding 仍然需要 BM25

向量检索擅长跨表述语义匹配：

```text
query：怎样隔离 Python 项目的依赖？
document：使用 venv 创建虚拟环境。
```

BM25 等稀疏检索擅长精确 token：

```text
ERR_CONNECTION_RESET
CVE-2026-1234
std::condition_variable
iPhone 17 Pro A3522
```

专有名词、版本号、报错码和函数名不应完全依赖稠密向量。稳妥做法是两路召回后按 ID 融合，而不是二选一。

### 为什么不能直接相加分数

BM25 分数没有固定上界，向量余弦常在有限区间内，两者分布还会随 query 变化。直接计算：

```text
0.5 * bm25_score + 0.5 * cosine_score
```

并不代表两路权重各占一半，BM25 的数值尺度可能完全支配结果。

Reciprocal Rank Fusion（RRF）只依赖每一路的排名：

\[
RRF(d)=\sum_i \frac{1}{k+rank_i(d)}
\]

下面是可运行实现：

```python
from collections import defaultdict

def reciprocal_rank_fusion(
    rankings: list[list[str]],
    rank_constant: int = 60,
) -> list[tuple[str, float]]:
    if rank_constant < 0:
        raise ValueError("rank_constant must be non-negative")

    scores: dict[str, float] = defaultdict(float)
    for ranking in rankings:
        seen: set[str] = set()
        for rank, document_id in enumerate(ranking, start=1):
            if document_id in seen:
                continue
            seen.add(document_id)
            scores[document_id] += 1.0 / (rank_constant + rank)

    return sorted(scores.items(), key=lambda item: (-item[1], item[0]))

bm25_ranking = ["doc-error-code", "doc-sse", "doc-http"]
vector_ranking = ["doc-sse", "doc-stream", "doc-error-code"]

fused = reciprocal_rank_fusion([bm25_ranking, vector_ranking])
for document_id, score in fused:
    print(f"{score:.6f}\t{document_id}")

assert fused[0][0] in {"doc-error-code", "doc-sse"}
```

`rank_constant=60` 是常见起点，不是不可调整的标准。两路召回深度、权重、去重规则和过滤条件都应通过验证集评估。权限、租户、时间等硬过滤必须在两路结果中一致执行，不能让一条路径绕过访问控制。

## 九、chunk 切错后，模型只能被动补救

整篇文档过长会混合主题；一句话一个 chunk 又可能丢失指代和条件。标题、表头、代码签名、合同编号如果与正文分离，向量模型收到的证据本来就不完整。

切块应遵循：

```text
文档结构决定边界
模型 tokenizer 决定最大输入
真实查询评估决定 size 和 overlap
```

具体实现和重叠召回问题见 [Chunk 学习笔记](/notes/ai模型开发/知识点学习/句子嵌入模型/chunk学习笔记/)。

## 十、从训练产物到可切换索引

一个可靠的离线建库任务至少包含：

```text
原始文档快照
  -> 清洗与结构解析
  -> chunk + metadata
  -> encode_document
  -> 向量文件 / 向量库 staging collection
  -> 构建 ANN 索引
  -> 数量、维度、范数、抽样召回检查
  -> 原子切换 alias
```

不要边生成边覆盖线上索引。一旦任务中途失败，线上会混合新旧向量。更安全的方式是创建不可变的新索引版本，完成校验后切换别名；旧版本保留到观察期结束，以便回滚。

### 建议的版本清单

```json
{
  "model_id": "embedding-2026-07-13-01",
  "base_model": "sentence-transformers/all-MiniLM-L6-v2",
  "model_revision": "pinned-commit-or-release",
  "tokenizer_revision": "pinned-commit-or-release",
  "preprocess_version": "preprocess-v3",
  "chunker_version": "chunker-v5",
  "dataset_snapshot": "kb-2026-07-12",
  "index_version": "kb-vector-2026-07-13-01",
  "dimension": 384,
  "normalized": true,
  "similarity": "dot_product_on_unit_vectors"
}
```

具体模型的维度必须从实际模型读取，上面的 384 仅对应示例模型，不是通用值。

### 新模型为什么通常必须重建文档向量

embedding 的坐标系由模型共同定义。即使新旧模型维度相同，坐标语义也未必兼容。用新模型编码 query、旧模型编码 corpus，相似度通常没有意义。

切换顺序应是：

1. 用新模型构建完整新索引；
2. 用固定 query 集验证新服务与新索引；
3. 同时切换 query encoder 和索引 alias；
4. 观察指标，异常时一起回滚。

只有经过专门训练的非对称双塔，才能有意使用不同 query/document encoder；这也不意味着可以随意混用版本。

## 十一、ANN 索引优化的不是同一个问题

小语料可以精确计算所有向量相似度，大语料通常使用近似最近邻索引（ANN）。HNSW、IVF、PQ 等方法在延迟、内存和召回率之间取舍。

这里有两个不同的 Recall：

- 模型检索 Recall：即使精确搜索，正确文档是否靠前；
- ANN Recall：近似索引能否复现精确向量搜索的邻居。

若不先做精确检索基线，就可能把模型问题误判为索引参数问题。调试顺序应是：

1. 在可控子集上精确检索；
2. 确认模型和数据能找到正确结果；
3. 再比较 ANN 与精确 top-k 的重合率；
4. 根据延迟预算调 ANN 参数。

## 十二、上线服务要测吞吐，也要测结果一致性

embedding 服务通常包括 tokenizer、批处理、模型推理、pooling、归一化和序列化。优化时应记录：

- P50、P95、P99 延迟；
- 不同长度和 batch size 下的吞吐；
- CPU、MPS 或 GPU 利用率；
- 超时、OOM 和截断率；
- 输出维度、dtype、范数分布；
- 固定探针文本的向量或相似度。

批次变大通常能提高吞吐，却会增加排队时间和显存。最佳 batch size 必须在目标硬件与真实长度分布上测量。

导出 ONNX、量化或改变精度后，不能只验证服务能启动。应对固定文本比较原模型与优化模型的向量偏差，并重新跑检索测试集。向量误差很小不一定代表排序完全不变，尤其是候选分数非常接近时。

## 十三、线上监控不能只有“平均相似度”

平均相似度会受 query 分布、语料规模和模型版本影响，单独看很难判断质量。监控应分层：

### 服务层

- 延迟、QPS、错误率、超时率；
- batch 大小、文本 token 长度、设备利用率。

### 检索层

- 空结果率、候选数、重复 chunk 比例；
- BM25 与向量结果重合率；
- reranker 前后的排序变化；
- 人工标注或弱反馈下的 Recall/点击指标。

### 向量层

- 向量维度和非有限值；
- 范数分布与相似度分布；
- 新旧版本固定探针的漂移；
- 索引中的模型版本是否与 query encoder 一致。

### 业务层

- 搜索点击、转化、改写率；
- RAG 答案采纳率、引用准确率和拒答率；
- 核心 query 类型的单独指标。

新 bad case 应回流为可复现的 query—相关文档标注，而不只是聊天截图。下一次模型、切块或索引变更都要自动重跑。

## 十四、常见症状与排查顺序

### 同义改写召回不到

先用精确向量搜索排除 ANN，再检查模型语种、训练数据和 query/document prompt。若 BM25 也失败，可能是语料根本没有正确答案。

### 错误码和函数名召回不到

保留 BM25 或其他稀疏召回，并检查清洗是否删除了符号、大小写和连字符。

### 离线很好，线上很差

对同一固定文本比较离线与线上向量，逐项核对 tokenizer、prompt、截断、pooling、归一化、dtype、模型 revision 和索引版本。

### top-k 全是相邻重复片段

检查 chunk overlap，按文档和区间去重，或采用小块召回后扩展邻居。不要只增大 K。

### 模型升级后全面退化

确认 corpus 是否用新模型重建、query encoder 是否同步切换，以及新模型是否要求不同 prompt。

### 总 Recall 提升，关键业务下降

按 query 类型和流量权重切片查看指标。平均分不能替代核心场景验收。

## 十五、一条务实的落地路线

从零构建知识库检索时，不必一开始就训练模型或引入复杂基础设施：

1. 明确 query、正确证据和延迟预算；
2. 建立小而可靠的 query—corpus—relevance 测试集；
3. 用现成 embedding 模型做精确检索基线；
4. 加入 BM25，并用 RRF 建立混合检索基线；
5. 做结构化 chunk、元数据过滤和结果去重；
6. 语料变大后再引入 ANN，单独测 ANN Recall；
7. 从 bad case 挖 hard negative，确有收益再微调；
8. 候选排序不足时增加 reranker；
9. 用不可变版本构建索引，灰度切换并保留回滚；
10. 将线上失败样本沉淀进固定评估集。

这条路线的重点是每一步都有前一版可比较的 baseline。否则模型、数据、chunk、索引和融合同时变化，出现提升或退化都难以归因。

## 总结

句子嵌入模型只是检索系统的一部分。它负责把文本映射到可比较的空间，却无法独自修复错误任务定义、破碎 chunk、假负样本、精确词漏召回或新旧索引错位。

可靠的落地方式是：用真实 query 定义相关性，用 query/document 一致的编码契约生成向量，用检索指标而非几个相似句验收，用 BM25 补足精确匹配，再把模型、预处理、语料和索引作为一个原子版本发布。

一句话概括：

> 模型决定语义表示的上限，数据决定它学到什么，检索链路决定这份能力能否真正到达用户。
